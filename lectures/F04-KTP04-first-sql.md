## Отношение кортеж и атрибут

Начнём с будущих данных магазина:

| product_id | title | price | quantity |
| --- | --- | --- | --- |
| 1 | Ноутбук | 50000.00 | 5 |
| 2 | Мышь | 1500.00 | 10 |
| 3 | Клавиатура | 3000.00 | 0 |

Одна строка описывает один товар. Столбцы отвечают на определённые вопросы: какой у товара идентификатор, как он называется, сколько стоит и сколько единиц осталось. По строке с номером 1 можно узнать все эти сведения о ноутбуке.

В реляционной модели отношение удобно представлять таблицей. Кортеж соответствует одной строке, атрибут — именованному столбцу. Для первых упражнений будем пользоваться этими соответствиями и сразу связывать термин с конкретным объектом на экране.

| Термин | Как увидеть в примере | Что обозначает |
| --- | --- | --- |
| Отношение relation | Таблица products | Набор записей с одинаковой структурой |
| Кортеж tuple | Строка про ноутбук | Значения атрибутов одного товара |
| Атрибут attribute | Столбец quantity | Свойство товара |
| Домен domain | Допустимые значения quantity | Целые числа от нуля и выше |

Домен описывает допустимые значения атрибута. Для остатка подходят 0, 5 и 10. Значение «пять» нарушает выбранный числовой тип, число −3 нарушает правило предметной области. У цены и остатка могут быть числовые типы, но смысл и правила этих атрибутов различаются.

В SQL тип и ограничения совместно помогают выразить допустимые значения. На этом занятии зададим простые правила непосредственно в описании столбцов.

Вопрос к вам: сколько кортежей показано в примере? Сколько атрибутов у каждого товара? Какой атрибут сообщает, что клавиатуры закончились? Здесь три строки, четыре столбца, а отсутствие товара на складе записано числом 0 в quantity.

В математическом отношении одинаковые кортежи не повторяются. SQL-таблица без подходящих ограничений допускает повторяющиеся строки. В нашей таблице за различимость записей будет отвечать первичный ключ. Порядок строк при обычной выборке заранее не гарантируется: сверяйте значения товаров, даже если они показаны в другом порядке.

## Схема и текущее состояние данных

Схема отношения описывает его имя, атрибуты, типы и ограничения. Например: products содержит идентификатор, название, цену и остаток; идентификатор уникален, название обязательно, цена и остаток имеют допустимые значения. Такая структура существует и у пустой таблицы.

Состояние отношения, или instance, — набор строк в определённый момент. Сейчас в таблице могут находиться три товара, после поставки — четыре. Изменение цены ноутбука меняет состояние данных. Добавление нового столбца изменило бы схему.

Слово «схема» встречается и в дереве pgAdmin: PostgreSQL объединяет объекты в именованные схемы, например public. В этом значении схема является пространством имён. В разговоре о schema/instance нас интересует описание структуры таблицы и её текущее содержимое.

Короткая практика: определите, что изменяется в каждом случае. Добавлен новый товар. Цена товара стала выше. В описание таблицы добавлен столбец цвета. В первых двух случаях меняются строки и значения, в третьем — структура. Сформулируйте это в notes.md одним предложением.

## Как SQL связан с PostgreSQL и pgAdmin

PostgreSQL — система управления базами данных. Сервер хранит данные, выполняет команды и проверяет ограничения. pgAdmin 4 — программа для подключения к серверу и работы с его объектами. Внутри pgAdmin мы откроем Query Tool и будем отправлять SQL-команды выбранной базе.

SQL расшифровывается как Structured Query Language. На этом языке можно описывать структуру и действия с данными. Например, запрос списка товаров задаёт нужную таблицу, столбцы и условия отбора. Способ выполнения запроса выбирает СУБД.

Для сегодняшней работы выделим следующие группы:

| Группа | Назначение | Команды занятия |
| --- | --- | --- |
| DDL Data Definition Language | Описание структуры | CREATE TABLE |
| DML Data Manipulation Language | Добавление изменение удаление данных | INSERT INTO, UPDATE, DELETE FROM |
| Чтение данных | Получение результата запроса | SELECT |

SELECT часто выделяют в DQL, язык запросов; в других классификациях его относят к DML. Для нашей практики важнее понимать выполняемое действие. После изменения данных будем читать результат отдельной выборкой. Команды изменения и удаления структуры рассмотрим позднее.

Записывайте ключевые слова заглавными буквами, а имена таблиц и столбцов — строчными латинскими буквами с подчёркиваниями. Завершайте команду точкой с запятой. Текстовые значения заключайте в одинарные кавычки: 'Ноутбук'. В записи десятичного числа используется точка: 1500.50. Переносы строк и отступы помогают читать длинные команды.

## Выбираем типы и первичный ключ

Для товаров используем integer, text и numeric(10, 2). Тип integer хранит целые числа, text — текст, numeric(10, 2) — точные десятичные числа с десятью цифрами всего и двумя цифрами после точки. Для учебной цены это позволяет записывать копейки; при записи PostgreSQL приводит значение к заданному масштабу.

Название товара может совпасть с названием другого товара. Чтобы точно выбрать конкретную строку, введём product_id. Этот столбец станет первичным ключом, PRIMARY KEY. Значения первичного ключа уникальны и обязательно присутствуют. По product_id можно будет однозначно обратиться к записи при изменении и удалении.

Поручим PostgreSQL выдавать идентификаторы автоматически. Для этого используется GENERATED BY DEFAULT AS IDENTITY. При обычной вставке пропустим product_id в списке полей. PostgreSQL возьмёт следующее значение из связанной последовательности. PRIMARY KEY дополнительно проверит его уникальность.

BY DEFAULT позволяет явно передать идентификатор. В обычных упражнениях используйте автоматическую выдачу; явное значение понадобится лишь в отдельном проверочном опыте. Вставка явного числа сама по себе не подстраивает последовательность под этот номер. Номера могут иметь пропуски, в том числе после неудачных вставок. По величине идентификатора количество товаров не определяют.

## Создаём таблицу товаров

Запишите определение таблицы в lesson04.sql:

```sql
CREATE TABLE products (
    product_id integer GENERATED BY DEFAULT AS IDENTITY
        PRIMARY KEY,
    title text NOT NULL,
    price numeric(10, 2) CHECK (price >= 0),
    quantity integer NOT NULL DEFAULT 0
        CHECK (quantity >= 0)
);
```

CREATE TABLE создаёт таблицу с указанным именем. В скобках перечислены столбцы: имя, тип и дополнительные правила. Запятые разделяют определения. После последнего определения запятая не требуется.

NOT NULL у title требует присутствия названия. CHECK (price >= 0) проверяет допустимость цены. У quantity одновременно заданы обязательность, значение DEFAULT 0 и проверка неотрицательного остатка. DEFAULT подставляется, когда столбец пропущен при вставке или явно запрошено его значение по умолчанию.

price оставлен необязательным: магазин может завести карточку товара до согласования цены. Это договорённость нашей предметной области. Смысл отсутствующей цены нужно будет учитывать при чтении и изменении данных.

Выполните только CREATE TABLE. Затем обновите через Refresh список Schemas → public → Tables в выбранной базе и найдите products. Если работаете в другой учебной схеме, откройте её список таблиц. Проверьте названия и типы четырёх столбцов.

Получим содержимое созданной таблицы:

```sql
SELECT * FROM products;
```

Звёздочка означает все столбцы, FROM указывает источник данных. Сейчас вывод содержит заголовки без строк. Схема уже существует, состояние данных пока пустое. Повторять создание этой же таблицы перед каждой вставкой не требуется: повторный CREATE TABLE сообщит о существующем объекте.

Практика. По аналогии создайте таблицу movies. Нужны movie_id с автоматической выдачей и PRIMARY KEY, обязательный title типа text, release_year типа integer и необязательный rating типа numeric(3, 1). Для rating добавьте CHECK (rating >= 0 AND rating <= 10). Слово AND соединяет два условия: оценка должна удовлетворять обоим. Выполните создание и прочитайте пустую таблицу.

## Добавляем строки

Первая вставка добавит ноутбук:

```sql
INSERT INTO products (title, price, quantity)
VALUES ('Ноутбук', 50000, 5);
```

После INSERT INTO указаны таблица и поля, после VALUES — их значения в том же порядке. product_id пропущен, поэтому PostgreSQL выдаст его автоматически. Выполните вставку один раз, затем повторите SELECT всех столбцов. В новой таблице первой записи обычно назначается номер 1; проверьте фактический результат.

Добавим ещё две записи одной командой:

```sql
INSERT INTO products (title, price, quantity)
VALUES
    ('Мышь', 1500, 10),
    ('Клавиатура', 3000, 0);
```

Каждая группа скобок содержит одну строку. Запятая между группами разделяет добавляемые товары. Снова получите все данные: при однократном выполнении вставок в исходно пустой таблице ожидаются три товара.

Теперь выберите только идентификатор, название и цену:

```sql
SELECT product_id, title, price FROM products;
```

Состав результата определяется списком после SELECT. quantity продолжает храниться в таблице. Выполните самостоятельно выборку title и quantity. Сопоставьте каждое число с нужным товаром.

Используйте автоматические movie_id. Получите все строки и отдельную выборку названий с оценками. Убедитесь, что добавлены именно три фильма.

## Разбираемся со смыслом NULL

NULL отмечает отсутствие известного значения. В нашей модели NULL в price будет означать «цена ещё не согласована». Значение 0 означало бы согласованную нулевую цену. Пустая строка '' является текстовым значением длины ноль. Для каждого допускающего NULL поля смысл отсутствия данных нужно определить заранее.

Добавим товар, для которого цена пока неизвестна, а остаток возьмём по умолчанию:

```sql
INSERT INTO products (title, price)
VALUES ('Коврик', NULL);
```

Получите все строки. Должны появиться четыре товара. У коврика price отсутствует, quantity равен 0, а идентификатор назначен автоматически. В pgAdmin отсутствие значения может отображаться специальной пометкой или визуально пустой ячейкой — ориентируйтесь также на результат запроса.

Обратите внимание: DEFAULT 0 подставился из-за пропуска quantity. Если явно передать NULL для quantity, проверка NOT NULL отклонит запись. Значение по умолчанию не заменяет явно переданный NULL.

Для поиска несогласованных цен используем специальную проверку:

```sql
SELECT product_id, title FROM products
WHERE price IS NULL;
```

WHERE задаёт условие отбора строк. IS NULL проверяет отсутствие известного значения. Для товаров с известной ценой напишите тот же запрос с IS NOT NULL.

Сравнение price = NULL даёт неизвестный логический результат. WHERE оставляет строки, для которых условие истинно, поэтому такая запись не найдёт ожидаемый товар:

```sql
SELECT product_id, title FROM products
WHERE price = NULL;
```

Выполните запрос и сопоставьте его с IS NULL. Пустой результат второго опыта объясняется правилами сравнения. Запишите в notes.md, какое условие нужно использовать при поиске неизвестной цены.

CHECK отклоняет значение, когда его условие ложно. При неизвестной цене сравнение price >= 0 имеет неизвестный результат, который CHECK допускает. Поэтому правило неотрицательной цены совместимо с разрешённым NULL. Когда значение обязательно, это отдельно задаётся через NOT NULL.

Короткая практика. Определите результат трёх ситуаций: цена 0; цена NULL; title равен ''. В первом случае известна нулевая цена, во втором цена неизвестна, в третьем передан пустой текст названия. NOT NULL само по себе допускает пустую строку; дополнительные требования к содержательности названия можно будет добавить отдельно.

## Читаем строки по условию

Перед изменением данных научимся выбирать нужный товар. Для первой строки используем идентификатор, который вы увидели в своей таблице:

```sql
SELECT product_id, title, price FROM products
WHERE product_id = 1;
```

В исходной последовательности это ноутбук. Если вы уже повторяли вставки, сверяйте фактические данные и используйте идентификатор нужной строки. Первичный ключ позволяет проверить, что условию равенства соответствует одна запись.

Получим товары дешевле 2000:

```sql
SELECT product_id, title, price FROM products
WHERE price < 2000;
```

Ожидается мышь. Коврик с неизвестной ценой в результат не попадёт: сравнение отсутствующей цены с числом имеет неизвестный результат. Количество найденных строк зависит от условия, текущих значений и состава таблицы.

Практика. Выберите фильм movies по его movie_id. Затем получите названия и оценки фильмов с rating >= 7.5. По первоначальным данным условию соответствует «Первый маршрут». Сначала предскажите результат и затем выполните запрос.

## Изменяем данные через UPDATE

Изменим цену ноутбука на 55000. Сначала выполните выборку с product_id = 1 и убедитесь, что нашли нужный товар. После этого запустите:

```sql
UPDATE products
SET price = 55000
WHERE product_id = 1;
```

UPDATE указывает таблицу, SET — изменяемый столбец и новое значение, WHERE — строки, к которым применяется действие. После выполнения снова прочитайте товар тем же SELECT. Должны сохраниться идентификатор, название и остаток, а цена станет 55000.00.

В отдельном упражнении увеличим остаток каждого товара на единицу. Сначала получите product_id, title и quantity всех товаров. Убедитесь, что намерены изменить все четыре строки, затем выполните:

```sql
UPDATE products
SET quantity = quantity + 1;
```

Правая часть использует старое значение quantity соответствующей строки. При исходных остатках 5, 10, 0 и 0 получатся 6, 11, 1 и 1. WHERE здесь пропущен осознанно, поскольку задача относится ко всем товарам.

Важно! UPDATE без WHERE изменяет все строки таблицы. Перед адресным изменением сначала выполняйте SELECT с тем же условием. В режиме Auto commit успешная команда сохраняется; отмена текста в редакторе не восстанавливает изменённые данные. Управление отменой изменений базы разберём при изучении транзакций.

Практика. Найдите movie_id фильма «Летний город». Прочитайте его по идентификатору, измените rating на 8.0 и повторно выполните ту же выборку. В notes.md укажите старую и новую оценку. Проверьте, что оценки остальных фильмов сохранились.

## Удаляем строки через DELETE

Удалим из учебного каталога товары дешевле 2000. Сначала снова выполните выборку с price < 2000. Убедитесь, что она показывает мышь. Затем используйте то же условие:

```sql
DELETE FROM products
WHERE price < 2000;
```

После удаления получите все товары и отдельно повторите выборку с price < 2000. В исходной последовательности останутся ноутбук, клавиатура и коврик; подходящих под условие цены строк больше нет. Структура products и её столбцы сохраняются.

Для адресного удаления используем идентификатор. Сначала прочитайте коврик по фактическому product_id. При последовательном первом выполнении до проверочных ошибок это номер 4. Затем удалите только эту строку:

```sql
DELETE FROM products
WHERE product_id = 4;
```

Повторите чтение по этому идентификатору и выборку всех товаров. Ожидаются две оставшиеся записи: ноутбук с остатком 6 и клавиатура с остатком 1. Идентификаторы могут иметь пропуски после удаления — это нормальное состояние.

Важно! DELETE без WHERE удаляет все строки указанной таблицы. Перед удалением используйте предварительный SELECT с тем же условием и проверьте выбранную базу. Пустая таблица продолжает существовать. Команду удаления самой структуры сегодня выполнять не требуется.

Практика. Прочитайте «Новый кадр» по его movie_id, удалите только этот фильм и проверьте результат. В movies должны остаться «Первый маршрут» с оценкой 7.5 и «Летний город» с оценкой 8.0. Сохраните выборку проверки рядом с командой удаления.

## Проверяем целостность данных

Целостность означает согласованность данных с правилами модели. В таблице товаров уже работают несколько таких проверок. Целостность сущности обеспечивается первичным ключом: у каждой строки есть уникальный обязательный идентификатор. Доменная целостность связана с допустимыми значениями: типами, обязательностью и CHECK.

Ссылочная целостность относится к согласованности данных между связанными таблицами. Например, если сотрудник отнесён к определённому отделу, сведения должны указывать на существующий отдел. Сейчас достаточно понимать смысл этого правила. Настройку и проверку межтабличных ссылок продолжим после освоения сегодняшних команд.

Выполните следующие опыты по одному. Сначала предскажите результат. После сообщения об ошибке прочитайте Messages и убедитесь обычной выборкой, что ошибочная строка отсутствует. Auto commit должен оставаться включённым; общую транзакцию для этих опытов не открывайте.

Первый опыт — повтор уже существующего первичного ключа ноутбука:

```sql
INSERT INTO products (product_id, title, price, quantity)
VALUES (1, 'Повтор номера', 100, 1);
```

PostgreSQL отклонит вставку из-за повторного product_id. Здесь явный номер используется специально для проверки. Подставьте фактический идентификатор ноутбука, если он отличается. Название товара само по себе первичным ключом не является.

Второй опыт — обязательное название отсутствует:

```sql
INSERT INTO products (title, price, quantity)
VALUES (NULL, 100, 1);
```

Третий опыт — отрицательный остаток:

```sql
INSERT INTO products (title, price, quantity)
VALUES ('Ошибочный остаток', 100, -1);
```

Четвёртый опыт — отрицательная цена:

```sql
INSERT INTO products (title, price, quantity)
VALUES ('Ошибочная цена', -10, 1);
```

Пятый опыт — текст, который не удаётся преобразовать к целому числу:

```sql
INSERT INTO products (title, price, quantity)
VALUES ('Ошибочный тип', 100, 'пять');
```

Во втором опыте срабатывает NOT NULL, в третьем и четвёртом — CHECK, в пятом — проверка преобразования значения к integer. Запишите причину каждого отказа короткой фразой. Отказ отдельной команды защищает таблицу от этого ошибочного изменения. Ранее успешно выполненные изменения сохраняются.

После неудачных вставок следующий автоматически выданный номер может оказаться больше ожидаемого. Проверяйте количество строк через результат выборки. Порядковый номер идентификатора не отражает количество успешных вставок.

Практика. В movies попробуйте изменить оценку существующего фильма на 11. Проверка диапазона должна отклонить изменение. Прочитайте фильм снова и убедитесь, что его прежняя оценка сохранилась. Исправьте команду на допустимое значение и выполните повторную проверку.
